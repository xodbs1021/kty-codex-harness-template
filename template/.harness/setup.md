# 설치 요청 한 번으로 적용 완료하기

사용자가 “하네스 설치해줘”, “README 읽고 적용해”, “설정 이어서 해줘”라고 요청하면
파일 설치 뒤 아래 절차까지 이어간다. 2·3·4단계를 다시 요청하도록 돌려보내지 않는다.
이것은 제공 Codex가 수행하는 작업 지침이며 설치 셸이 AI 작업까지 실행했다는 뜻이 아니다.
설치만 요청받았다면 실제 문제의 기능 구현·제출은 시작하지 않는다.

## 1. 현재 상태부터 복구

- `AGENTS.md`, `.harness/setup-status.md`, `.harness/state/setup-context.json`을 읽는다.
  context의 과제·반입 경로가 여전히 존재하는지 확인한다. 경로가 옮겨졌으면 실제 경로로 갱신한다.
- 기존 프로필·checks·근거와 완료 기록을 보존한다. 실행 결과가 있고 대상이 동일한 단계는 반복하지 않는다.
  대상 변경·실패·근거 없음이면 해당 단계만 다시 수행한다. 대기 항목을 이유 없이 완료로 바꾸지 않는다.
- “읽기 전용”은 현재 세션 정책·도구 오류·대상 경로 중 무엇의 제한인지 구분한다.
  정책이 명시적으로 금지하면 쓰기를 시도하지 않는다. 금지되지 않았다면 설치 명령의 실제 결과로 판단한다.
  리뷰 전용 자식은 설치 주체가 아니다. 메인 세션과 자식의 권한이 같다고 추측하지 않는다.
  실패한 명령·대상·짧은 오류를 남긴다. 권한·샌드박스·신뢰 설정을 우회하지 않는다.
- 일반 파일 쓰기와 `.codex`·`.agents` 설정 경로 쓰기는 별개다. workspace-write라는 이름만으로
  전체 설치 가능하다고 가정하지 않는다. `--no-hooks`도 두 설정 경로에 쓰므로 제한을 해결하지 않는다.
- 사용자가 터미널에서 이미 설치했다면 manifest와 실제 파일을 확인하고 설치기를 반복하지 말고
  아래 과제 설정부터 이어간다. 미설치이고 설정 경로가 보호된 경우, 운영 환경이 허용하는
  사용자 터미널 설치 명령을 실제 경로로 안내한다. 해당 터미널의 권한이 더 넓다고 단정하지 않는다.
  일반 쓰기가 가능한 부분은 문서형 설정으로 진행하고 전체 읽기 전용이면 결과를 응답으로 남긴다.

## 2. 과제 설정 — 현재 세션에서 먼저 수행

- `.agents/skills/kty-harness/SKILL.md`, `.harness/project-profile.md`, `.harness/principles.md`를 직접 읽는다.
  Skill 자동 발견이 안 돼도 파일 읽기가 가능하면 절차를 적용한다. 직접 읽기를 자동 등록이라고 보고하지 않는다.
- 실제 과제 README·기존 지침·관련 코드에서 도메인·필수 요구·스택·실행 경로·제출물을 확인해
  **`.harness/project-profile.md`**를 갱신한다 (`project.profile.md`가 아니다).
  확인된 과제 사실만 기록하고 미확인 업무 기준은 가정·영향을 표시한다.
- `.harness/task-evidence.md`에 요구·확인 출처·관찰 기준을 연결한다.
- 실제 테스트·빌드 명령을 프로젝트 문서와 설정에서 확인해 `.harness/checks.json`에 argv 배열로 등록한다.
  기존 명령을 보존·검토한다. 배포·외부 전송·데이터 파괴 명령을 검증으로 실행하지 않는다.
  명령이 없으면 빈 검사·항상 성공하는 marker를 만들어 통과시키지 말고 미검증으로 기록한다.
  관련 검증 방법이 없는 문제라면 가능한 실제 입력·출력 확인과 그 한계를 기록한다.
- 반입본의 `knowledge/semiconductor/README.md`, `application-playbook.md`를 읽어 사용법과 실제 경로를 남긴다.
  65개 본문 전체를 시작 때 읽지 않는다. 과제와 관련된 개념만 색인으로 찾는다.
- 실제 명령을 등록했다면 `python3 .harness/harness.py verify`를 실행한다.
  실패는 실패로 남긴다. 설치 범위에서 고칠 수 있는 경로·명령 설정 오류는 고치되 과제 코드의 실패를 숨기지 않는다.

## 3. 런타임 연결 — 가능한 일을 끝낸 뒤 필요한 조치만 요청

- 현재 세션의 실제 모델·effort·네이티브 역할·훅 지원을 제공 도구의 정보로 확인한다.
  설정 파일은 의도이며 현재 모델의 증거가 아니다. effort를 임의로 고정하지 않는다.
- 역할 파일 복사, Skill 직접 읽기, 자동 발견, 실제 호출을 구분한다. 자동 발견이 안 돼도
  직접 읽기와 사용 가능한 독립 리뷰 방식으로 계속한다.
- 새 세션이 필요한 경우 현재 진행을 setup-status에 기록한다. 사용자가 터미널에서
  `cd <확인한 과제 루트> && bash .harness/codex.sh`를 실행하도록 실제 경로로 한 줄을 제공한다.
  이 실행기는 기본 요청문으로 이 문서와 상태를 읽고 남은 작업을 이어가게 한다.
  에이전트 도구에서 인터랙티브 Codex를 중첩 실행하거나 현재 대화를 임의 종료하지 않는다.
- `/hooks`·`/status`는 지원하는 Codex UI의 명령이다. 셸 명령처럼 실행하지 않는다.
  CLI가 없거나 제공 UI에 명령이 없으면 플랫폼의 지원 여부를 미확인/환경 제한으로 기록한다.
- 훅 정의는 사용자가 정상 `/hooks` 절차로 검토·신뢰한다. 자동 신뢰나 우회 플래그를 쓰지 않는다.
  근거가 없으면 “등록, 신뢰 미확인, 실제 실행 미확인”으로 적는다.
  실제 콜백은 런타임 로그·이벤트 근거로 확인한다. `hook`에 이벤트 JSON을 직접 넣은 것은 모의 시험이다.
  설치 확인을 위해 실제 과제에 고의 결함을 넣지 않는다. 별도 훅 차단 실험은 사전체험 runbook에서 수행한다.
- 훅·재시작을 기다리는 동안 가능한 검증·리뷰를 먼저 한다. 해당 한 가지 제약 때문에 전체 작업을 멈추지 않는다.

## 4. 실제 검증과 Sol + Sol 독립 리뷰

- 리뷰 범위는 **설치한 설정, 실제 요구와 프로필의 일치, 등록한 검증 명령**이다.
  설치 확인을 전체 과제 해결 완료로 확대하지 않는다.
- `.agents/skills/kty-harness/references/roles.md`의 A/B 계약을 따른다.
  `python3 .harness/harness.py fingerprint`로 대상을 기록하고 두 리뷰가 끝날 때까지 수정하지 않는다.
- 제공된 독립 역할을 사용할 수 있으면 Sol 두 독립 컨텍스트를 호출한다.
  네이티브 역할이 없고 제공 Codex CLI가 사용 가능하면 `harness.py review`를 별도 두 번 실행한다.
  이는 비대화형 읽기 전용 검수이며 인터랙티브 메인 중첩 실행과 다르다.
  각 요청에 동일한 실제 대상·요구·판정 기준을 넣고 A는 계약·회귀, B는 입력·권한·실패 경계를 중심으로 본다.
  양쪽에 이전 리뷰 응답·작성자의 정당화를 주지 않는다. 응답은 `.harness/work/`에 보관한다.
- 실제 호출 ID 또는 로그, 실제 모델 정보, 대상 지문, 두 응답을 확인하고 합친다.
  호출 실패나 모델 확인 불가를 Sol 듀얼 리뷰 성공으로 표시하지 않는다. 같은 세션에서 두 번 읽는 것은 대체 검수다.
- 설치 범위의 타당한 지적은 고친 뒤 영향 범위를 재검토한다. 전체 실패를 무한 재시도하지 않는다.
  시간 부족·환경 제한은 남은 작업으로 표시한다.
- 프로필·checks·task-evidence를 최종 갱신한 **뒤** verify를 실행해 최신 영수증을 남긴다.
  setup-status를 포함한 검증 대상 파일을 이후 수정하면 다시 검증한다.
  마지막 검증 결과·리뷰 상세는 지문에서 제외되는 `.harness/work/`에 남겨 영수증을 스스로 만료시키지 않는다.

## 5. 완료 보고

설치 경로 / 프로필·근거 / 실제 검증 결과 / Skill / 모델·effort / 역할 / 훅 / 리뷰 A·B /
남은 사용자 조치를 짧게 보고한다. 완료·실패·미지원·미확인을 분리한다.
기능 활성화가 막혔어도 읽고 적용한 프로필과 수동 검증의 범위를 명확히 알린다.
진행 기록의 `이어갈 작업`을 갱신하여 새 세션이 이미 끝낸 검토를 무조건 반복하지 않게 한다.
