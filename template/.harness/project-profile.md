# 프로젝트 프로필 — SK하이닉스 AI 해커톤 2026

이번 해커톤 전용 프로필이다. 과제 유형 대비 관점 갱신일은 2026-10-31이며 재설치 시 보존한다.
운영 안내에서 확인한 조건, 사용자가 선택한 하네스 정책, 실제 접속 전 미확인 사항을 구분한다.
과제 접속 후에는 기존 프로젝트 지침·README·실제 코드와 화면을 읽고 미확인 항목을 갱신한다.
공개 데모의 도메인·스택·점수를 실제 과제 요구로 옮기지 않는다.

## 1. 목표와 사용자

- 목표: 제공된 Probe 작업 공간에서 실제 업무 문제를 정의하고, 작동하는 구현과 검증 근거를 제출한다.
- 사용자 대면 언어: 한국어. 구현 결과뿐 아니라 중요한 선택·대안·실패 조건·한계를 설명한다.
- 평가 대비 관점: 결과의 동작, 목표와 AI 위임, 본인의 설명을 함께 준비한다.
  정확한 채점 항목·배점은 미확인이다.
- 구체적인 업무 도메인·필수 동작·제출 파일: 미확인 — 과제 README에서 확인한다.
- 요구·출처·성공 조건·구현·실제 관찰: `.harness/task-evidence.md`에 연결한다.
  과제 지정 문서가 있으면 그 문서를 정본으로 삼고 경로를 연결한다.

## 2. 작업 환경과 도구

- 운영 안내: 브라우저 안의 웹 IDE·터미널·미리보기·업무 메신저와 제공 Codex를 사용한다.
- 사용자 선택: 메인·검수 모델은 GPT 6.1 Sol. effort는 고정하지 않고 허용된 실제 설정을 따른다.
- 개인 API 키·개인 구독·Claude Code·별도 외부 AI를 실행 환경에 연결하지 않는다.
- 업무 의미·처리 기준은 업무 담당자, 화면·도구·제출 절차는 Cofa Helper에 확인한다.
- 오류·접속 장애는 제공된 문제 신고 절차를 사용하고 발생 단계·오류·시각을 기록한다.
- OS·셸·Python·Git·Codex 버전·설치 권한·외부 다운로드 범위: 미확인.
- 과제 언어·런타임·패키지 매니저·소스·테스트 진입점: 미확인.
  기존 도구를 먼저 사용하고, Python 하네스를 쓴다는 이유로 과제 스택을 Python으로 바꾸지 않는다.

## 3. 설치와 실행 원칙

- 운영 안내에서 공개 GitHub 도구의 clone·다운로드와 터미널 설치를 안내한다.
  실제 쓰기 경로·OS 패키지 설치 권한·다운로드 대상별 접근 가능 여부는 접속 후 확인한다.
- 전체 기능은 Bash·Python 3.9 이상·Git·제공 Codex를 사용하며 Python 외부 패키지는 필요 없다.
- 반입 경로는 허용된 쓰기 가능한 곳을 택한다. 작업 공간 밖 `/tmp`는 필수 경로가 아니다.
  내부 반입 예시는 `.harness/vendor/kty-codex-harness/`이며 설치기는 이 경로를 Git에서 제외한다.
- 기존 과제 Git 루트에 설치한다. Git 작업 공간이 아니면 임의 초기화하지 않고 확인한다.
- Python이 없거나 설치가 허용되지 않으면 반입한 하네스 패키지 README의 문서형 모드로 진행한다.
  이 경우 프로젝트 자체 명령으로 검증하며 Python 영수증·훅이 실행됐다고 보고하지 않는다.
- 패키지·도구 설치를 위해 권한을 확대하거나 제공 Codex·감독·보안 설정을 바꾸지 않는다.

## 4. 구현과 검증

- 의미 있는 변경은 실패 재현이나 실제 입력·출력으로 확인한다. 명령의 정본은 `.harness/checks.json`이다.
- 요구마다 성공 조건·현재 코드 위치·실제 결과를 연결하고 미실행·부분 충족을 구분한다.
- 데이터 제외·변환은 이유와 핵심 결과의 영향을 확인한다. 업무상 중복·재시도·부분 실패 등은 관련될 때 검증한다.
- 수동 화면 확인은 응시자가 플랫폼 미리보기에서 수행한다. AI 실행과 응시자 확인을 구분한다.
- 과제 유형 대비: 서비스·API 구현뿐 아니라 제공 환경에 연결해 실제 응답과 동작을
  확인하는 작업이 요구될 수 있다. 이는 대비 관점이며 본시험의 출제 내용이 확정됐다는 뜻은 아니다.
- 주소·바인딩·포트·경로·접속 도구·연결 절차는 고정하지 않는다. 현재 과제 안내·README·
  실행 설정·실제 출력으로 확인하고, 과거 체험이나 안내 예시를 그대로 적용하지 않는다.
  서비스 과제라면 실행 → 연결 → 요구된 응답·동작 확인까지 계획과 검수에 포함한다.
  상세 적용 기준은 Skill의 `references/probe-workflow.md`를 따른다.
- 아키텍처·데이터·입출력 불변식과 모듈 경계: 미확인 — 실제 업무 기준을 확인해 채운다.

## 5. Sol + Sol 독립 검수 정책

- 같은 코드 상태를 별도 컨텍스트의 Sol 두 개로 검수한다. 두 리뷰 모두 정확성과 보안을 본다.
- A는 요구·계약·호출자·회귀, B는 공격 경로·잘못된 가정·권한·입력 경계·실패 조건에 중점을 둔다.
- 첫 검토가 끝나기 전에는 서로의 결론이나 작성자의 정당화 내용을 전달하지 않는다.
  실제 요구·대상 코드·판정 기준·프로필·원칙을 공통 입력으로 준다.
- 메인이 지적을 `[A]`·`[B]`·`[A·B]`로 합쳐 재현·판단하고, 수정 뒤 영향 범위를 재검수한다.
  단순 다수결이나 반복 횟수로 통과시키지 않는다.
- 역할 계약과 호출 방법은 `.agents/skills/kty-harness/references/roles.md`를 따른다.
  두 독립 실행이 없으면 듀얼 리뷰 미실행으로 보고한다. 같은 세션 전환·완료 감사는 두 번째 리뷰가 아니다.
- effort·독립 역할·별도 CLI 가용성은 사전 체험에서 확인한다. 차단 시 실패와 대체 검수 범위를 밝힌다.

## 6. 시간과 제출

- 운영 안내상 과제 작업은 최대 180분이다. 실제 화면의 남은 시간과 전체 종료 시각을 우선한다.
- 필수 경로를 먼저 완성하고 마지막 10분은 검증·문서·저장·제출 확인에 배분한다.
  과한 설치·문서·반복 검수로 필수 동작과 최종 검증을 밀어내지 않는다.
- 저장 상태·필수 파일·최신 검증·미해결 한계를 확인한다. 실제 화면 제출은 응시자가 직접 한다.
- 작업 단계에서 구현 흐름·판단 이유·한계를 설명한다. 이해 확인이 없으면 이해 완료로 기록하지 않는다.
- 후속 서술형 단계에 들어가면 AI 지원을 종료하고 응시자가 직접 답한다.

## 7. 외부 경계와 사전 체험

- 시험 문제·파일·결과를 외부로 보내거나 push·PR·게시하지 않는다. 기존 Git 이력·remote를 보존한다.
- 공개 도구는 제공 환경 안에서 가져온다. 본시험 Computer Use는 사용하지 않는다.
- 사전 체험 환경 분석은 사용자가 전달한 허용 범위에 따라 본시험과 구분한다.
- 사전 체험은 안내상 1회 15분이다. 도구 버전·쓰기 경로·공개 반입과 설치를 먼저 확인하고,
  모델·effort·독립 검수·훅·미리보기·저장·종료 흐름을 점검한다. 긴 환경 구축으로 체험을 소진하지 않는다.
- 공개 배포본에는 실제 과제·답안·접속 코드·개인 인증 정보·첨부 운영 문서 원문을 넣지 않는다.

## 8. 정본과 진행 상태

- 공학 원칙: `.harness/principles.md`
- 평가 과제 절차: `.agents/skills/kty-harness/references/probe-workflow.md`
- 실제 검증 명령: `.harness/checks.json` — 다른 문서에 명령 정본을 중복 관리하지 않는다.
- 진행 상태: `.harness/work/progress.md`, 검수 결과: `.harness/work/review.md`
- 외부 개인 지식 저장소 의존은 없다. 과제 작업 공간 안의 사실과 확인된 결정을 사용한다.

## 9. 선행 결정·조사·설명의 연결

- 선행 결정 진입점은 실제 과제 README·기존 AGENTS.md·이 프로필·task-evidence.md와
  `.harness/work/clarifier-qa.md`, `progress.md`다. 존재하는 자료만 읽고 개인 vault·claude-mem은 요구하지 않는다.
- 개발 착수 전 clarifier가 중요 모호함을 확인한다. 조사 필요성을 판단하고 필요한 경우
  collector와 evaluator를 분리한다. 채택 근거를 설계·계획에 연결하고 별도 plan-reviewer가 확인한다.
- 변경 설명은 실제 diff·검증 결과에 근거해 사용자에게 전달한다. 구조 설명 질문은 architecture-guide가 담당한다.
- 완료 감사는 위 단계의 실제 근거와 미실행을 확인한다. 자동 훅과 별개의 역할 절차다.
- 실행 순서와 상세 계약의 정본은 Skill의 `references/workflow.md`, `research.md`, `explanation.md`다.
