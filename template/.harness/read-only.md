# 설치 없는 하네스 루틴

전체 설치가 불가능할 때 사용하는 절차다. 파일 읽기·검사·독립 리뷰·완료 대조를
가능한 범위에서 한 요청 안에 수행한다. 설치·코드 수정·자동 훅을 대체했다고 주장하지 않는다.
이 문서는 파일 쓰기나 자동 발견을 요구하지 않는다.
역할과 호출 흐름은 반입본 `template/.agents/skills/kty-harness/references/workflow.md`를 따른다.
설치가 안 됐다고 명료화·조사·설명 역할을 생략하지 않는다. 문서형 모드의 권한 제한을 우선 적용한다.

## 경로와 권한

- 과제 루트와 반입 저장소 루트를 실제 README·현재 위치로 확인한다.
  아래 `template/` 경로는 반입 저장소 기준이다. 설치본이 이미 있으면 해당 파일도 읽되
  새 설정이 필요하다는 이유로 보호 경로에 다시 설치하지 않는다.
- 전체 읽기 전용이면 설치기·파일 복사·기록 저장·권한 변경을 하지 않는다.
  주어진 정책을 검증하려고 쓰기를 시도하지 않는다. 진행·판단·검증 기록은 대화에 남긴다.
- 일반 파일만 쓰기 가능한 경우에도 `.codex`·`.agents`를 다른 위치로 옮겨 우회하지 않는다.
  허용된 기록 파일만 선택적으로 사용할 수 있다. 이 루틴은 그 파일의 존재에 의존하지 않는다.
- 메인과 자식의 실제 권한을 구분한다. 읽기 전용이 해제돼야 하는 구현·설치 단계는
  대기 상태로 남기고, 사용자가 허용된 경로로 수행해야 할 정확한 작업을 마지막에 설명한다.

## 한 요청으로 수행할 순서

1. **지침 로드.** `template/.harness/project-profile.md`, `template/.harness/principles.md`,
   `template/.agents/skills/kty-harness/SKILL.md`와 `references/roles.md`를 직접 읽는다.
   이 문서의 쓰기 없는 절차를 적용하고, 원문 중 설치·기록 저장·verify 영수증·자동 훅 지시는
   읽기 전용에서 실행하지 않는다. 자동 등록 없이 지침을 읽은 상태라고 표현한다.
   workflow.md로 요청을 분류하고 필요한 역할 TOML·research.md·explanation.md를 직접 읽는다.
   코드·문서 작업이면 반입본 `template/.agents/skills/google-styleguide/SKILL.md`와
   해당 원문을 읽고, 설명·문서는 `readable-writing/SKILL.md`도 읽는다.
   API 설계·구현·검수는 `template/.agents/skills/google-api-design/SKILL.md`와 관련 원문도 읽는다.
   설치된 경로가 없다는 이유로 해당 스킬을 생략하지 않는다.
   새 작업이면 decision-memory.md에 따라 과제 내부 과거 시도와 이미 반입된 기준본을
   한 번 대조한다. 기존 이력·기준본 부재는 미확인으로 남기며 쓰기·외부 접속으로 보충하지 않는다.
   역할 이름 미등록이면 같은 지침을 제공 독립 도구에 전달하고 실제 응답을 기다린다.
   workflow의 역할별 새 컨텍스트·부모 대화 상속 차단 계약을 적용한다. `fork_turns` 지원 시 `none`을 명시한다.
   독립 도구가 없으면 순차 대체 수행과 독립 실행 미수행을 구분한다.
2. **실제 과제 프로필.** 과제 요구·스택·제약·입출력 계약·검증 명령·미확인 항목을
   README·코드에서 확인한다. 파일 저장 없이도 이 사실을 공통 검토 입력으로 유지한다.
   해커톤 운영 템플릿의 사실을 다른 과제 요구로 옮기지 않는다.
   지식 패키지는 반입본 README·적용 가이드를 먼저 읽고 필요한 개념만 색인으로 찾는다.
3. **명료화·조사·계획과 실행 경계.** 개발 요청이면 clarifier 판정부터 남긴다.
   선행 결정으로 답이 안 되는 중요 질문만 메인이 사용자에게 전달한다.
   조사 필요/불요/실패를 판단하고 필요하면 collector → 별도 evaluator의 원문 대조를 수행한다.
   요청이 조사나 설명뿐이면 workflow의 해당 경로로 완료하고 개발 단계는 실행하지 않는다.
   설계/계획이 필요하면 작성자와 plan-reviewer를 분리하고 결과를 대화에 남긴다.
   요구와 성공 조건을 연결한다. 설치·적용만 요청받았다면 이 연결과
   현재 검증 경로를 대상으로 검토한다. 실제 구현을 요청받았더라도 전체 읽기 전용에서는
   코드 변경을 완료할 수 없으므로 분석·검토와 필요한 변경안을 응답으로 제공한다.
   변경안을 작성한 것을 적용·테스트 완료로 표시하지 않는다.
   변경안까지 요청받았다면 제공 독립 도구에 developer 지침을 전달해 응답으로 후보를 받는다.
   이때 developer도 읽기 전용이며 설치된 `harness.py role developer`를 요구하지 않는다.
   후보에 식별자·내용 지문을 붙이고 검사·A/B·설명·감사에 같은 버전을 전달한다.
   디스크의 기존 코드와 응답의 후보 코드는 별도 검증 대상으로 유지한다.
4. **실제 검사.** 과제의 기존 검사 중 파일·캐시·DB·빌드 산출물 등을 쓰지 않는 명령만 실행한다.
   필요하면 도구가 문서화한 캐시 비활성화 옵션을 사용한다. Python 표준 unittest라면
   `PYTHONDONTWRITEBYTECODE=1 python3 -B -m unittest discover -s tests -v`처럼
   바이트코드 생성을 끌 수 있다. 테스트 코드 자체의 쓰기 부작용까지 없어진다는 뜻은 아니다.
   쓰기가 필요한 빌드·테스트는 미실행과 이유를 남긴다. 별도 저장 공간을 찾아 우회하지 않는다.
   `.harness/harness.py verify`는 영수증을 쓰므로 이 모드에서는 실행하지 않는다.
   스타일 검사는 반입본의 `check_style.py --root <실제 과제 루트>`를
   `python3 -B`로 직접 실행할 수 있다. 파일을 쓰지 않으며 Go 포맷만 검사한다.
   도구 부재·실행 금지는 미검증으로 남긴다. 다른 언어는 원문·제공 검사와 대조한다.
   실행 명령·종료 코드·실제 출력 요약을 대화에 남기고, 검사 실패를 통과로 바꾸지 않는다.
   후보 코드를 검사할 때는 파일 저장 없이 `python3 -B -c '<검사 코드>'` 같은 방식으로
   메모리 내에서 실행할 수 있다. 코드 문자열은 안전하게 인자로 전달하고 셸 치환을 유발하지 않는다.
   zsh의 heredoc(`<<`)·here-string(`<<<`)은 임시파일 쓰기를 유발할 수 있으므로 사용하지 않는다.
   셸 단계에서 막힌 실행과 실제 Python 검사 실패를 구분하고, 권한 변경 없이 쓰기 없는 방식으로만 복구한다.
   후보 검사 통과는 디스크 적용·저장·제출 성공이 아니다. 기존 파일 검사가 실패하면 그 결과도 남긴다.
5. **독립 리뷰 A·B.** 앞 단계에서 쓸 수 없었던 파일이 있다는 이유로 리뷰까지 생략하지 않는다.
   제공 도구가 새 컨텍스트의 독립 에이전트를 지원하면 두 번 실제 호출하고 완료를 기다린다.
   설치한 `kty_reviewer` 이름을 요구하지 않는다. 현재 도구가 지원하는 역할로 공통 역할 지침을 전달한다.
   모델을 선택할 수 있고 허용된다면 `gpt-6.1-sol`을 사용한다. effort는 강제하지 않는다.
   A는 요구·계약·회귀, B는 입력·권한·오류·실패 경계를 중심으로 정확성과 보안을 검토한다.
   동일한 실제 대상 파일·요구·판정 기준을 주고 서로의 첫 결론·작성자의 정당화는 전달하지 않는다.
   파일을 수정하거나 결과를 저장하지 말고 응답으로 반환하도록 한다.
   가능한 읽기 전용 해시 도구로 검토 대상의 전후 내용을 대조하며 해시 목록도 파일에 쓰지 않는다.
   호출 ID·양쪽 결과·모델 관찰 근거를 남긴다. 요청 모델과 실제 모델 확인을 구분한다.
   독립 호출 기능이 없거나 차단되면 같은 세션 검토를 수행하되 독립 듀얼리뷰 미실행으로 표시한다.
   개인 인증·외부 AI 연결이나 CLI 설치로 이 한계를 해소하려 하지 않는다.
   실패 시에도 문제·파일·코드·로그·결과를 외부 MCP·개인 vault 등으로 옮기지 않는다.
   실제 보안 경계·테스트 품질 검토가 필요하면 workflow의 조건부 역할도 수행한다.
   한쪽에만 있는 고위험 지적은 교차 검증하고 미확정은 해결로 바꾸지 않는다.
   cross-verification.md의 단일 지적 범위·기각 의존 파일 해시를 적용한다.
   해시·판정은 대화에 남기고 파일 기록을 요구하지 않는다. 변경된 의존 파일의 옛 기각은 재사용하지 않는다.
6. **병합·설명과 완료 감사.** A/B 지적을 근거로 합쳐 타당성을 확인한다. 수정이 필요하면
   미해결 항목과 변경안을 제시한다. 기존 내용이 바뀌지 않았다면 같은 테스트를 무조건 반복하지 않는다.
   실제 변경이 있으면 change-explainer로 설명하고 사용자에게 전달한다.
   변경이 없다면 변경 설명은 불요로 표시하고 분석 결과·한계는 메인이 설명한다.
   설계 이유 질문에는 architecture-guide를 직접 사용한다.
   마지막에 auditor가 명료화·조사 판정·필요한 계획 검토·검사·A/B·조건부 검토·설명 근거를 대조한다.
   별도 auditor 호출이 없으면 메인의 완료 대조임을 표시한다. 파일 기록 대신 실제 대화 근거를 사용한다.
   검사 실패·미검증·환경 제한·미해결 차단 지적이 있으면 전체 완료를 선언하지 않는다.

## 마지막 응답 형식

- 적용 범위: 설치 없는 지침 적용 / 저장·구현 가능 여부.
- 실제 과제 프로필: 요구·계약·검증 경로와 미확인 사항을 짧게 정리.
- 단계 상태: 명료화·조사/평가·설계/계획 검토·설명·감사의 수행/불요/미실행과 이유.
- 검사: 실제 명령·종료 코드·통과/실패/미실행 및 이유.
- 리뷰 A/B: 각 호출 식별자·독립 여부·모델 확인 수준·핵심 지적과 병합 판단.
- 완료 대조: 충족/미충족/미검증, 설치·수정·훅에 필요한 남은 조치.
- 다음 세션 인계: 반입 경로·과제 경로·다음 작업. 파일 저장이 안 됐음을 명시.

**마지막 대조는 지침에 따른 점검이다. 자동 Stop 훅·강제 게이트·검증 영수증이 아니다.**
전체 읽기 전용에서 파일 구현·저장까지 포함한 완전한 개발 루틴은 수행할 수 없다.
새 세션은 이 대화를 자동으로 이어받는다고 가정하지 않는다. 필요한 경우 사용자가
반입본 README와 이 문서를 다시 읽도록 요청한다. 하위 작업 실패가 있으면 그 결과를 보고하고
가능한 다른 단계를 계속하되 무한 재시도하지 않는다.
