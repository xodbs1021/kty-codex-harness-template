# Google 기준 공통 API 설계

Python·Java·Go 등 구현 언어와 별개인 서비스 계약을 다룬다.
Google AIP 중 과제에 필요한 부분을 선택해 적용하는 하네스 계약이며, Google 인증이나
전체 AIP 준수를 뜻하지 않는다. [출처·라이선스](references/NOTICE.md)를 유지한다.

## 먼저 읽고 적용하기

1. 실제 과제 README·OpenAPI/Proto·기존 코드·테스트·선행 결정을 읽어 외부 계약을 확인한다.
   명시적 과제 요구·플랫폼 제약·기존 호환 계약을 우선한다. 충돌은 근거와 예외로 남기며,
   Google 형식에 맞추려 기존 URL·필드·상태 코드·응답을 조용히 바꾸지 않는다.
2. [적용 기준](references/application.md)과 [원문 선택표](references/source-map.md)를 읽는다.
   API 작업은 AIP-121의 설계 원칙을 읽고, 작업에 해당하는 AIP의 Guidance와 관련 하위 절을
   **로컬 원문에서 직접 읽는다.** 선택표만 읽고 원문을 읽었다고 보고하지 않는다.
   기존 기록으로 이어갈 때는 같은 원문 버전·내용의 읽기 근거를 확인한다.
3. 역할에 따라 아래 결과를 반환한다. 전체 읽기 전용이면 파일을 쓰지 않고 대화로 반환한다.
   설치본이 없으면 반입본 `template/.agents/skills/google-api-design/`를 직접 읽는다.
   누락·읽기 실패는 미확인으로 남긴다. 시험 과제·코드를 외부 도구로 보내지 않는다.

## 역할별 산출물

- **설계·계획:** 실제 리소스/메서드/경로, 요청·응답, 오류·인가, 관련될 때 페이지·중복 요청·
  동시 수정·호환 계약을 정한다. 선택한 AIP와 적용/예외 이유, 구체적 입력·기대 결과를 연결한다.
  새 API라도 사용하지 않을 기능·인프라를 지침 목록을 채우려고 추가하지 않는다.
- **구현:** 승인된 계약과 선택한 AIP 원문을 확인하고 과제의 언어·프레임워크로 구현한다.
  코드 스타일은 별도 `google-styleguide` Skill을 따른다.
- **설계/계획 리뷰·코드 리뷰 A/B:** 각각 독립적으로 관련 원문을 읽고 계약/코드/테스트와 대조한다.
  작성자의 “Google 준수” 주장이나 다른 리뷰 결론을 근거로 대신하지 않는다.
  지적마다 AIP 번호·절, 대상 위치, 적용 이유와 구체적 실패 입력/영향을 연결한다.
  원문의 must/should/may와 과제 예외를 구분하며 취향 차이를 기능 결함으로 과장하지 않는다.
- **보안·테스트 검토:** 해당 범위의 원문만 읽고 권한 경계·오류 노출·재시도·경계 사례를 검토한다.
- **완료 감사:** 읽기·적용·실행을 따로 확인한다. 단순 문서 존재나 스타일 검사 성공을 API 검증으로
  세지 않는다. 단독 지적 교차 검증이면 해당 지적에 필요한 원문만 읽어 기존 축소 범위를 유지한다.

각 결과에 `API 근거: AIP 번호/읽은 로컬 경로·절 → 계약 또는 코드 위치 → 적용/예외/미확인 →
검증 입력·기대 결과·실제 결과(미실행이면 사유)`를 짧게 남긴다.
설계 단계의 검증 계획을 실제 실행 결과로 표현하지 않는다.
메인은 쓰기 가능할 때 기존 design/plan/review/audit 또는 task-evidence에 연결하고,
읽기 전용에서는 해당 대화 결과를 후속 역할에 전달한다. 새 영수증이나 별도 대장을 강제하지 않는다.

API와 무관하면 `API 지침: 적용 대상 아님(이유)` 한 줄로 끝낸다.
이 Skill은 자동 API linter나 실행 강제 훅이 아니다. 필요한 검사는 실제 과제 도구로 수행한다.
