# 요청 분류와 실행 흐름

메인이 순서를 조율하고 역할은 맡은 단일 임무의 결과를 반환한다. 역할 파일 존재와 실제 독립 호출을 구분한다.
프로필·원칙·실제 요구·대상 경로·허용 작업·성공 조건·남은 시간을 공통 입력으로 준다.
설치본 경로가 없으면 반입본 `template/`의 동일 파일을 직접 읽고, 과제 경로는 별도로 전달한다.

## 요청 분류

- 설치·설정만 요청: `.harness/setup.md`를 따른다. 과제 구현으로 확대하지 않는다.
- 기능 구현·수정·리팩터링: 아래 1–6단계. 작은 작업은 산출물을 짧게 하되 판단 단계를 생략하지 않는다.
- 계획만 요청: 1–3단계의 명료화·조사 판단·설계/계획·A/B 검토까지 수행하고 계획과 한계를 반환한다.
  구현·배포·제출로 확대하지 않는다. 이미 계획이 있으면 실제 변경·새 요구에 필요한 부분만 갱신한다.
- 검수만 요청: 요청된 설계/계획/코드 게이트의 A/B와 조건부 검토·지적 통합으로 직접 간다.
  코드 수정은 하지 않고 지적·근거를 반환한다. 수정까지 요청된 경우에만 구현 단계로 돌아간다.
- “이어서”, “검수만 다시” 등 부분 재실행: progress·실제 파일·이전 결과로 완료 근거를 회수한다.
  대상 변경·실패·근거 누락에 영향받는 단계만 재개한다. 전체 파이프라인을 무조건 재시작하지 않는다.
- 조사·비교 요청: [research.md](research.md)의 수집 → 독립 평가 → 메인 종합.
- 변경 설명: `kty_change_explainer`에 실제 diff를 전달한다.
- 구조·설계 이유·“남이 물으면 어떻게 설명하지”: `kty_architecture_guide`를 호출한다.
- 단순 조회는 직접 답한다. 정보 부족·숨은 가정·범위 충돌을 발견하면 `kty_clarifier`로 명료화한다.

초기 실행의 과거 시도 회수·기준본 대조, 중요 결정·단계 전환·반복 지적은
[decision-memory.md](decision-memory.md)를 적용한다.

## 호출과 기록

필요한 논리 역할마다 별도 컨텍스트를 사용한다. 짧은 요청이나 작은 과제에서도 clarifier와 planner를
한 자식에 묶거나, 완료된 자식을 followup으로 developer 등 다른 역할로 전환하지 않는다.
불필요한 역할은 이유와 함께 생략하고, 필요한 역할의 독립성을 줄여 호출 수를 절약하지 않는다.
같은 역할의 부족한 정보 보완은 후속 요청으로 이어갈 수 있지만 새 역할·새 A/B pass는 새 호출이다.
도구가 `fork_turns`를 지원하면 모든 역할 호출에 `fork_turns="none"`을 명시한다.
부모 대화 전체를 상속하는 기본값에 의존하지 않고, 과제 경로·역할 지침·필요한 선행 산출물만 전달한다.
특히 리뷰 A/B에는 작성자의 정당화나 다른 리뷰의 첫 결론을 포함하지 않는다.
컨텍스트 분리를 지원하지 않거나 확인하지 못하면 그 한계를 표시하고 독립 검수 완료로 세지 않는다.

1. 제공 네이티브 역할이 있으면 대응 역할을 새 컨텍스트로 호출하고 실제 결과를 기다린다.
2. 이름이 등록되지 않아도 독립 도구가 있으면 해당 TOML 지침과 이 Skill의 관련 reference를 직접 전달한다.
3. 제공 Codex CLI와 설치본을 정상 사용 가능하면 `harness.py role <역할> '<실제 요청>'`으로 읽기 전용 독립 호출한다.
   `developer`는 이 읽기 전용 실행기의 대상이 아니다. 구현은 쓰기 허용된 메인 또는 제공 developer가 한다.
   전체 읽기 전용에서 변경안 작성을 요청받으면 제공 독립 도구에 developer 지침을 직접 전달해
   응답으로 후보만 받는다. 후보 내용 지문을 검사·리뷰·설명에 전달하며 적용 완료로 보고하지 않는다.
4. 독립 호출 자체가 불가능하면 메인이 같은 계약을 순서대로 수행하고 **독립 실행 미수행**을 표시한다.
   이름 변경·역할 연기·같은 대화의 두 응답을 독립 검증으로 세지 않는다.

메인이 `.harness/work/`에 `clarifier-qa.md`, `research/collected.md`, `research/evaluated.md`,
`design.md`, `plan.md`, `design-review.md`, `plan-review.md`, `review.md`, `explanation.md`, `audit.md`,
`progress.md`를 필요한 단계에만 기록한다. 전체 읽기 전용이면 이 제목과 실제 호출 ID·결과를 대화에 남긴다.
자식은 결과를 반환하고 공유 문서를 수정하지 않는다. 메인은 원문 결과와 합친 판단을 구분한다.
호출 기록에는 역할·단계·실제 호출 ID·대상 버전/지문·대화 상속 설정·성공/실패를 연결한다.
독립 실행 여부는 자식 수나 역할 이름만으로 판정하지 않는다.

호출 미지원·실패·시간초과·검사 명령 실패는 각각 구분하고, 미응답을 지적 0건이나 승인으로 바꾸지 않는다.
이미 실행 중인 호출을 중복 생성하지 않는다. 원인이 바뀌지 않은 재시도는 멈추고 가능한 다른 단계와
같은 세션의 대체 검수를 진행하되 독립 실행 미수행/미완료를 남긴다.
대체 경로도 제공 시험환경 안에 한정한다. 문제·파일·코드·로그·결과를 외부 MCP·개인 AI·개인 vault로
보내거나 push·PR·업로드하지 않는다. 도구 반입 허용을 작업물 반출 허용으로 해석하지 않는다.

## 1. 명료화 — kty_clarifier

개발 착수 전에 원문 요청을 전달한다. 먼저 실제 과제 README·프로필·이전 문답·업무 담당자 답변을
확인한다. 원본의 개인 메모리 대신 현재 과제 안의 선행 결정을 회수한다.
질문 0건이어도 `사전 결정 회수: <경로·결론 또는 없음(사유)>`, `판정: 명확 | 확인 필요`를 남긴다.
코드로 알아낼 사실은 직접 확인한다. 범위·숨은 가정·성공 기준·이전 결정과의 충돌 중 사용자만
결정할 수 있는 것만 선택지·추천 이유와 함께 최대 3–4개로 반환한다. 질문이 목적이 아니다.
질문은 메인이 실제 사용자에게 전달하고 필요한 답이 오기 전에는 해당 결정에 의존하는 작업을 하지 않는다.
기존 명시적 승인·답변을 다시 요구하지 않는다. 구현 중 새 모호함이 생겨도 이 단계로 돌아온다.

## 2. 조사 필요 판단 — 수집과 평가 분리

공개 선례·공식 사양·대안·실패 사례에 따라 설계가 달라질 수 있는지 판단한다.
필요하면 [research.md](research.md)의 collector → evaluator를 실행하고 채택 근거만 설계·계획에 전달한다.
불필요하면 구체적인 이유, 실패하면 시도·장애·영향을 남긴다. 필요 판단 없이 조사를 조용히 생략하지 않는다.
설계·계획 머리에 `사전 결정 회수:`와 `레퍼런스 조사: 조사함(...) | 불요(...) | 실패(...)`를 적는다.
형식만 채우지 말고 관련 결정·근거가 본문 어디에 반영됐는지 연결한다.

## 3. 설계·계획과 별도 검토

새 모듈·레이어, 데이터 모델·경계 변경, 여러 모듈에 걸친 구조 변경이면:
`kty_architect` 설계 → 별도 `kty_plan_reviewer` Sol A/B 두 컨텍스트에서 설계만 검토 →
`kty_planner` 구현 계획 → 다시 새 plan-reviewer Sol A/B 두 컨텍스트에서 계획과 설계 정합성 검토.
비구조적 작업도 planner → 별도 plan-reviewer A/B로 진행한다. 각 pass는 동일 산출물을 검토한다.
A는 요구·선행 결정·계약, B는 가정·실패 조건·보안 경계·검증 누락에 중점을 두되 공통 기준은 같다.
서로의 첫 결론을 전달하지 않는다. 입력 독립성은 roles.md의 A/B 계약을 따른다.
설계·계획의 구조/세부 분류·이월·종결 조건은 [plan-gates.md](plan-gates.md)가 정한다.
교차 검증은 cross-verification.md의 단계별 적용 범위를 따른다.
작성자의 자기검토나 단일 reviewer를 듀얼 승인으로 세지 않는다.

관측 동작이 관련되면 이벤트마다 로그 등급과 실패 신호를 정하고 gauge의 설정·해제 조건을 함께 검토한다.
설계는 모듈 경계·입출력 계약·불변식·대안·장단점을, 계획은 파일·구현 단계·검증 입력/기대 결과·위험·시간을 담는다.
검토자는 실제 코드와 원칙을 읽고 요구 누락·과설계·영향 경계·테스트 구체성·선행 결정 반영을 검증한다.
조사 불요 사유와 인접 분야 배제 이유도 검토한다. 근거가 본문에 반영되지 않았으면 지적한다.
`판정: 승인 | 보류`, 구조/세부·설계/문서 분류, 차단 지적·권고·실패 시나리오를 반환한다.
보류면 작성자가 수정한다. 조사 문제는 2단계로, 입력 지침 누락은 메인이 입력을 고쳐 같은 검토로 돌아간다.
시간·환경 제약으로 해결 못 한 차단은 남겨 보고하며 임의 승인하지 않는다. 진전 없는 반복은 중단한다.

## 4. 구현·검증·Sol + Sol 검수

메인 또는 `kty_developer`가 승인된 범위에서 구현한다. 관련될 때 실패 재현·테스트부터 확인하고
실제 사용한 방법·결과를 남긴다. 설치되지 않은 TDD 플러그인을 호출했다고 쓰지 않는다.
Google 스타일 Skill과 작업 언어 원문을 먼저 읽고 구현·리뷰에 적용한다.
기존 검증 명령을 사용하며 전체 설치 시 checks.json → verify로 스타일·실제 과제 검사 결과를 남긴다.
reviewer와 auditor도 안전하게 실행 가능한 관련 검사를 직접 수행한다.
부작용·권한 때문에 실행할 수 없으면 기존 로그 대조와 직접 실행 미검증을 구분한다.
두 독립 Sol 리뷰의 계약은 [roles.md](roles.md)를 따른다. A/B 모두 정확성과 보안을 보되 중점을 달리한다.

조건부 역할도 누락하지 않는다:
- 인증·인가·사용자 입력·DB 쿼리·파일·외부 API·시크릿 등 보안 경계 변경: `kty_security_reviewer` 별도 검토.
- 새 기능·버그 수정에서 테스트가 핵심 방어선이거나 검수자가 검증력을 의심: `kty_test_analyzer` 별도 검토.

한쪽 A/B에만 있는 CRITICAL/HIGH 지적은 상대편의 새 검토로 구체적 반례·재현을 교차 확인한다.
[cross-verification.md](cross-verification.md)를 읽고 단일 지적에 한정한 반박 검증을 수행한다.
기각 기록을 재사용할 때는 모든 의존 파일의 워킹트리 해시와 시나리오가 여전히 같은지 확인한다.
변경·삭제·빈 의존 목록·새 의존 경로·확인 불가이면 새 검증으로 돌아간다.
재현됨은 수정, 현상 부재는 근거와 함께 기각, 심각도만 낮아지면 해당 수준으로 보존한다.
미확정은 미해결로 남긴다. 두 사람이 말했는지보다 코드·실제 실행 근거가 우선이다.
보안·테스트 지적도 근거로 판단하고 `[A]`, `[B]`, `[A·B]`, `[security]`, `[test]` 출처를 유지한다.
메인은 통합 `판정: 통과 | 보류`와 지적별 처리를 남기고 수정 후 영향 범위를 재검증한다.
관련 변경 범위에서 같은 결함 유형을 찾아 함께 처리했는지 검색·회귀 근거로 확인한다.
후속 검토에는 그 근거와 미해결 사례를 전달한다. 요청 밖 선재 개선이 섞이지 않았는지 대조한다.
원본의 무지적 횟수 채우기·PR 반복·자동 push는 시험용 흐름에 넣지 않는다.

## 5. 변경 설명 — kty_change_explainer

[explanation.md](explanation.md)에 따라 실제 diff·검증 결과·결정 근거를 전달한다.
메인은 설명을 사용자에게 실제 전달한다. 파일에 저장만 한 것은 설명 완료가 아니다.
사용자의 이해가 확인되지 않았으면 이해 완료로 쓰지 않는다. 설명 도중 미검증 동작이 드러나면 검증 단계로 돌아간다.

## 6. 완료 감사 — kty_auditor

작성자와 별도 컨텍스트에서 실제 요구·코드·검증·위 단계 결과를 대조한다.
명료화 판정(질문 0건 포함), 조사 판정과 근거, 필요한 설계/계획 검토, A/B 실제 호출,
조건부 보안/테스트 검토, 지적 처리, 사용자에게 전달한 설명을 확인한다.
각 단계는 `수행 / 불요(이유) / 미실행(이유)`로 구분한다. 설치만 요청한 경우 과제 전체 파이프라인을 요구하지 않는다.
호출 기록의 역할 분리와 대화 상속 설정도 확인한다. 역할 전환·부모 전체 대화 상속을 독립 호출로
잘못 센 경우 해당 주장을 보류하고 필요한 새 검토를 요구한다. 기록을 확인할 수 없으면 미확인이다.
전체 설치는 최신 영수증을, 문서형은 실제 명령·종료 코드·검토 시점의 대상 상태를 확인한다.
근거가 없으면 완료 주장을 보류하고 메인에게 부족한 검증을 요구한다. 감사자가 기록을 만들어 통과시키지 않는다.
기각 재사용의 의존 해시·단독 반박 범위·미확정 처리·같은 결함 유형의 수정 근거도 대조한다.
메인은 사용자에게 핵심 결과·필요한 결정·검증 근거·한계와 상세 기록 위치를 짧게 보고한다.
실제 저장·화면 확인·제출은 별개이며 후속 서술형 단계에서는 AI 지원을 종료한다.

이 흐름은 역할 실행 계약이다. 자동 훅이 모든 단계의 수행을 강제하거나 증명하는 것은 아니다.

## 단계·검토 결과 보고

단계 전환·계획·검토·완료 보고에서 사용자가 읽을 핵심, 사용자만 결정할 항목
(없으면 없음), 상세 근거의 위치와 다시 볼 조건을 먼저 구분해 짧게 전달한다.
전체 읽기 전용이면 상세 근거 위치는 파일 대신 대화의 단계/지적 ID로 지정한다.
다음 검토 전에 A/B 판정과 지적별 수정·기각·미해결 처분, 요청 범위 내 수정 여부를 알린다.
보고만을 이유로 별도 승인을 새로 요구하거나 턴을 끊지 않는다. 실제 필요한 판단만 기다린다.
