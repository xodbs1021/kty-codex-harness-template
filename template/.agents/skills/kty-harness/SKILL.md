# Codex 개발 하네스

메인 실행기는 Codex, 모델은 `gpt-6.1-sol`, 추론 강도는 `xhigh`다.
`.harness/project-profile.md`와 `.harness/principles.md`를 먼저 읽는다.
이미 진행 중이면 `.harness/work/progress.md`에서 이어간다.
업무·필수 파일·시간 제한은 과제 README와 현재 사용자 지시를 기준으로 확인한다.
실무 평가 과제의 요구 확인·구현·제출 점검에는 [probe-workflow.md](references/probe-workflow.md)를
읽고 `.harness/task-evidence.md`에 요구·판단 출처·실제 관찰을 연결한다.
진행 문서에는 상태를, 근거 문서에는 요구별 판단을 남겨 같은 내용을 중복 작성하지 않는다.

## 역할과 근거 전달

역할별 계약은 [roles.md](references/roles.md), ECC 적용 기준은
[ecc-quality.md](references/ecc-quality.md)에 있다. 해당 단계에서 필요한 부분만 읽는다.
프로필은 도메인 사실의 정본이고 원칙은 판정 기준의 정본이다.
역할을 분리할 때 관련 프로필 내용과 원칙, 대상 파일 경로를 함께 전달한다.

Codex는 `.codex/agents/`에서 `kty_planner`, `kty_developer`, `kty_reviewer`, `kty_auditor`를 발견한다.
제공 환경이 멀티에이전트를 지원하고 허용하면 계획 검증·코드 검수·완료 감사는
각각 별도 컨텍스트의 대응 역할에 위임한다. 현재 단계의 대상·판정 기준·읽을 경로를 전달한다.
구현은 메인이나 명확한 파일 범위를 받은 developer가 수행한다.
동시에 쓸 파일이 겹치지 않게 하고 활성 역할은 필요한 최소 수로 유지한다.
해당 기능이 없거나 차단되면 그 제한을 보고하고 같은 세션에서 역할을 순서대로 수행한다.
독립 컨텍스트의 리뷰를 실제 실행했을 때만 독립 리뷰라고 보고한다.
메인과 위임한 역할 모두 같은 모델·추론 강도를 사용한다.
네이티브 자식은 부모의 실제 권한을 상속한다. 역할의 수정 금지 지침은 샌드박스가 아니다.
파일 쓰기를 기술적으로 차단해야 하는 검수·감사는 아래 명령으로 독립 실행한다.
응답을 받은 메인이 검수 문서에 기록한다. 실행이 차단되면 권한을 넓히지 않고 보고한다.

```bash
python3 .harness/harness.py review '검수할 변경과 판정 기준'
python3 .harness/harness.py audit '대조할 완료 주장과 근거'
```

두 명령은 전체 Codex 프로세스에 `--sandbox read-only`를 적용한다.

## 요구사항 확인과 계획

1. 실제 코드와 README를 읽고 목표·제출물·제약·필수 동작을 확인한다.
   프로필의 지식 진입점이 있으면 관련 결정만 따라간다.
2. 이미 결정된 사항을 다시 묻지 않는다. 구현 방향을 바꾸는 미확인 요구만 질문한다.
   시험 업무 맥락은 제공된 실무자 에이전트, 화면 사용법은 Cofa Helper를 활용한다.
3. 구조가 바뀌면 모듈 계약·데이터 흐름·대안·선택 이유를 먼저 정리한다.
4. `.harness/work/plan.md`에 목표, 확인한 선행 결정과 출처,
   영향 파일, 구현 단계, 단계별 검증, 위험과 남은 시간을 적는다.
   각 필수 요구의 성공 조건과 근거 ID를 계획에 연결한다.
5. plan-reviewer 역할로 필수 요구 누락·잘못된 가정·경계 불일치를 확인한다.
   사소한 수정은 이 내용을 짧게 합쳐 기록한다.

## 구현과 검증

- 프로젝트의 기존 도구와 코드를 먼저 사용한다. 검증할 동작이 있는 변경은
  실패 재현이나 의미 있는 테스트를 만들고 구현한다.
- 실제 검증 명령을 `.harness/checks.json`에 등록한다.
  형식은 `{"checks":[{"name":"test","argv":["npm","test"],"timeout_seconds":120}]}`다.
  명령은 프로젝트 루트에서 실행된다. 파이프·리다이렉션 등 셸 문법은 자동 해석하지 않는다.
- `python3 .harness/harness.py verify`를 실행한다. 실패 원인을 고친 뒤 재검증한다.
  명령이 하나도 없거나 실행하지 못했으면 검증 완료로 보고하지 않는다.
- 실제 코드의 입력·오류·경계·회귀를 reviewer 역할로 검사한다.
  인증·입력·DB·파일·외부 API 변경이면 관련 보안 항목도 확인한다.
  지적은 경로·구체적인 입력과 실패 결과·심각도를 적고 타당성을 확인해 고친다.
- 화면 기능은 응시자가 플랫폼 Browser 미리보기에서 직접 확인한다.
  서버는 제공 환경 안내대로 바인딩하고 실제 포트·경로를 전달한다.

## 완료와 시간 관리

- `.harness/work/review.md`에 검수 결과와 미해결 항목을 적는다.
- `.harness/work/progress.md`에 결정·선택 이유·검증 근거·다음 작업을 갱신한다.
- 종료 전 최신 코드의 검증 성공, 필수 파일과 저장 상태, 미완료 항목을 확인한다.
  변경 후에는 이전 검증 영수증을 재사용하지 않는다.
- 180분 과제라면 필수 동작 우선으로 계획하고 마지막 10분은 검증·문서·제출에 남긴다.
  반복 검수 횟수를 채우려고 구현·검증 시간을 소진하지 않는다.
- 사용자에게 구현 결과, 실행 방법, 검증 결과, 선택 이유, 남은 한계를 설명한다.
  AI의 제안·실행과 응시자의 직접 판단·확인을 구분하고, 이해 여부를 추정하지 않는다.
  후속 서술형에서는 AI가 답변하지 않는다.

## 시험 환경 경계

공개 도구는 제공 환경 안에서 가져온다. 문제·파일·작업 결과를 외부에 보내거나
push·PR·게시하지 않는다. 개인 API 키·외부 AI·다른 모델 연결은 사용하지 않는다.
브라우저·컴퓨터 자동 조작은 본시험에서 사용하지 않는다.
허용된 사전 체험 분석의 범위는 사용자가 전달한 운영 안내를 따른다.
제공 환경의 승인·감독·보안·연결 설정은 유지하고 차단 시 신고 절차를 따른다.

## 기계 검증의 범위

네이티브 SessionStart·Stop 훅이 설치·신뢰된 환경에서는 현재 세션의 파일 변경 뒤
검증 영수증이 없거나 오래되면 Stop 시 검증 실행을 요청한다.
훅 활성화는 `/hooks`에서 확인한다. 훅이 없으면 위 검증 명령을 명시적으로 실행한다.
이 장치는 검증 명령의 종료 코드와 코드 지문을 확인한다.
요구사항 충족·테스트 품질·실제 이해·독립 리뷰까지 증명하는 장치는 아니다.
