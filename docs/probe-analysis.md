실제 응시 세션에 접속하거나 시험 문제를 조사한 결과가 아니다.

## 공개 데모에서 관찰한 구체적인 신호

평가 데모의 예시 응시자 A는 기술 86·의도 66·인지 76, 총 228/300이다.
각 축의 핵심 예시로 데이터 전처리, AI 위임 범위, 구현 선택의 이유를 보여준다.
이는 설명용 예시 수치이며 **SK하이닉스의 배점·합격선·전체 평가 항목이 아니다.**

제품 페이지에서 사후 Q&A·소스코드·작업 로그 탭을 직접 전환해 확인했다.
누락 데이터 제외의 이유와 집계 영향, AI에 맡긴 일과 직접 확인한 부분을 묻는다.
예시 코드는 누락값을 확인한 뒤 행을 제외하지만, 영향 비교와 이유 설명은 부족하다고 평가한다.
따라서 단순 테스트 통과나 실행 성공만으로 판단의 적절성이 입증되지는 않는다고 해석했다.

[공개 작업 공간 데모](https://www.getcofa.com/brochure-v2/workspace-mock.html)는
주문 API 안정성 과제와 README·소스·테스트·판단 문서, Codex 터미널, 업무 담당자 채팅을 보여준다.
화면 예시에서는 확인되지 않은 결제를 취소해도 되는지 묻자 담당자가 중복 결제 방지를 우선하며
결과 확인까지 대기하는 방향을 설명한다. 이를 업무상 불변식과 모호함을 확인하는 사례로 해석했다.
이 화면은 설명용 구성이다. 주문·결제 도메인이나 특정 스택이 실제 출제된다는 근거는 없다.

## 기존 하네스의 빈틈과 반영

| 기존 지원과 빈틈 | 이번 보완 |
| --- | --- |
| 계획·검수·검증 영수증은 있으나 요구별 성공 조건과 근거 연결이 느슨함 | `.harness/task-evidence.md`에 요구 출처·성공 조건·코드·실제 관찰을 연결 |
| 선택 이유 기록은 있으나 응시자 판단과 AI 제안을 혼동할 가능성 | 판단 출처·검증 주체·미확인 상태를 구분하고 감사 역할이 대조 |
| 명령 성공이 데이터 처리나 업무상 결정의 적절성까지 보장하지 않음 | 관련 변경에서 결과 영향 비교와 업무상 반례를 검수 |
| 설명 제공을 응시자 이해로 간주할 가능성 | 작업 단계에서 코드에 근거한 설명과 본인 이해 확인을 제안하고 미응답은 미확인 유지 |
| 작업 문서와 지정 제출물의 관계가 불명확 | 과제 지정 문서를 정본으로 연결하고 제출 전 필요한 근거를 반영 |

추가 네트워크·API·모델·MCP·자동 기록 수집기를 도입하지 않는다.
새 문서는 재설치로 지워지지 않는 프로젝트 슬롯이다. 기존 검증 훅의 판정 범위는 바꾸지 않았다.
표에 적었다고 요구 충족·본인 이해가 자동 입증되는 것은 아니다.
실제 출력과 작업 기록에 맞춰 짧게 유지하고, 형식을 채우기 위해 허위·사후 기록을 만들지 않는다.

## 실제 환경에서 남은 확인

- SK하이닉스 해당 회차의 정확한 채점 항목·배점·과제별 성공 조건.
- 제공 모델·Codex 버전, Skill 발견, 독립 역할·훅·별도 CLI 실행 가용성.
- 업무 담당자와 Helper의 역할, 미리보기·데이터·실행·제출 경로.
- 지정 문서·작업 공간 파일·중첩 CLI 기록의 수집 범위. 공개 소개만으로 세부 범위를 확정할 수 없다.

다른 행사인 [Cofathon](https://cofathon.getcofa.com/)의 도구·업로드 허용 안내는
SK하이닉스 운영 규칙으로 전용하지 않는다. 현재 과제와 운영 안내가 우선한다.
하네스의 읽기 전용 검수·감사 응답은 메인이 작업 중 정리하며, 그 별도 세션까지
플랫폼이 수집한다고 주장하지 않는다. 후속 서술형 단계에는 AI 지원을 종료한다.
