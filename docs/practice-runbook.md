# 사전체험 15분 실행표

준비일: 2026-10-28. 이 문서는 사전체험용이다. 실제 Probe에서 검증한 결과가 아니다.
태윤이가 Dot와 Probe를 조작하고, 외부 관찰자는 화면을 읽으며 다음 입력과 판정만 안내한다.
관찰자는 클릭·타이핑·명령 실행을 하지 않는다. 아래 명령의 실행 주체는 태윤이 또는 제공 Codex다.

로컬 리허설 1회에서는 중간 실패 복구·최종 보고까지 **14분 21초**가 걸렸다.
성공한 듀얼 검수는 두 별도 CLI 세션이었다. 초기 프롬프트만으로 끊김 없이 끝난 것은 아니며,
실제 사용자 타이핑·Probe UI는 측정하지 않았다. [실측과 한계](timed-rehearsal.md)를 참고한다.

## 시작 전에

- 아직 15분 체험을 시작하지 않은 화면에서 Dot 관찰 연결부터 확인한다.
- 기억할 것은 GitHub 아이디 `xodbs1021`과 **환경 → 설치 → 훅 → 두 리뷰 → 정리** 순서다.
- `/status`의 작업 권한을 먼저 확인한다. 읽기 전용이면 제공 UI에서 허용된 작업 모드를
  선택할 수 있는지 확인한다. 관리 제한이 있으면 권한·네트워크를 임의 확대하지 않고 Helper에 문의한다.
- URL·이 문서·파일을 외부에서 붙여넣어야 한다고 가정하지 않는다. 첫 요청으로 공개 저장소를 찾고,
  반입한 저장소 README에서 이 문서를 읽게 한다. 실패하면 짧은 1단계 입력문을 그대로 직접 입력한다.
- 상위 운영 안내가 정한 실제 남은 시간을 우선한다. 각 시간은 목표이지 완료 보장이 아니다.

| 경과 | 목표 | 관찰자가 확인할 증거 |
| --- | --- | --- |
| 0–3분 | 아이디로 공개 저장소 탐색·clone, 도구·쓰기 경로 확인 | 정확한 저장소·commit, 명령의 실제 출력·오류 |
| 3–5분 | 독립 검증 폴더 준비, 프로젝트·훅 신뢰, 세션 재시작 | fixture 경로, `/status`, `/hooks`의 두 훅과 신뢰 상태 |

| 7–11분 | Sol 두 독립 컨텍스트로 같은 코드를 검수 | 서로 다른 실제 호출·응답·모델, 같은 코드 지문 |
| 11–13분 | 보고서·미지원 항목 정리 | 아래 판정표에 근거와 미확인 상태 기록 |
| 13–15분 | 미리보기·저장·체험 종료 흐름 여유 | 남은 UI 항목을 직접 확인하고 체험 종료 |

3분까지 탐색/반입이 안 되면 반복 검색 대신 오류를 기록하고 Helper에 허용 경로를 확인한다.
Python이 없으면 긴 설치·빌드로 시간을 쓰지 않는다. 5분까지 준비되지 않으면 훅은 미확인으로
남기고 가능한 네이티브 독립 리뷰·환경 확인으로 넘어간다. 11분 이후에는 새 리뷰를 시작하지 않는다.
문제가 생긴 경로는 한 번 원인을 확인하고, 제한 우회나 같은 재시도를 반복하지 않는다.
Sol capacity 오류는 실제 시간 예측을 깨뜨릴 수 있다. 다른 모델로 바꾸지 않고 오류·시각을 기록한다.
저장소가 이미 반입됐다면 사용자 터미널에서 준비기·아래 CLI 대체 경로를 직접 실행할 수 있다.
두 리뷰도 완료되지 않으면 미완료로 남기고, 15분 성공을 보장한다고 해석하지 않는다.

## 입력 1 — 아이디로 발견하고 검증 폴더 준비

제공 Codex에서 Sol을 선택하고 입력한다. effort는 기본을 유지하며 표시된 실제 값을 기록한다.

> 사전체험 15분이야. GitHub 사용자 xodbs1021의 공개 Codex 하네스 저장소를 찾아 README의 ‘사전체험 15분 실행표’를 읽어줘. 허용된 작업 공간에 clone하고 Python·Git·Codex 버전을 확인한 뒤 검증 폴더만 준비해줘. 원래 연습 과제와 보안 설정은 건드리지 말고, 새 세션을 여는 명령과 검증 폴더 경로를 알려줘. 외부 API 키·추가 모델·effort 강제·장시간 설치는 하지 마.

저장소를 찾은 제공 Codex는 아래 작업만 한다.

1. GitHub 공개 계정 API의 저장소 목록에서 이름·설명으로 `kty-codex-harness-template`을 식별한다.
   계정 목록은 내려받은 응답을 재사용한다. Google 검색 노출에 의존하지 않는다.
   계정 목록 접근이 안 되면 GitHub 검색 등 허용된 경로를 한 번 확인하고 실패 근거를 남긴다.
2. 새 반입 경로에 clone하고 실제 commit과 `pwd`, Python·Git·Codex 버전을 기록한다.
   API 조회와 Git clone의 실제 네트워크 가용성을 각각 확인한다.
   OS·권한을 바꾸거나 기존 경로를 덮어쓰지 않는다. 로컬 리허설의 권한 선택을 Probe 정책에 전용하지 않는다.
3. 반입한 패키지 안의 허용된 `tmp/` 폴더를 만들고 아래 준비기를 실행한다.
   명령 속 경로는 실제 반입 경로로 바꾼다.

```bash
python3 <반입경로>/scripts/practice_probe.py prepare <반입경로>/tmp
```

준비기는 그 안에 **새 임시 Git 프로젝트 하나**를 만들어 하네스를 설치한다.
원래 연습 과제에 `git init`하거나 그 과제의 코드·검증 명령을 바꾸지 않는다.
이 설치 성공은 해당 검증 폴더의 결과다. 실제 과제 폴더에서의 설치·기존 설정 병합은 별도 확인 대상이다.
출력 JSON의 `fixture` 경로를 기억한 뒤 제공 Codex는 현재 턴을 끝낸다.
반입 경로와 보고 명령은 검증 폴더의 `.harness/state/practice-fixture.json`에도 저장한다.
새 세션에는 이전 대화가 없으므로 필요한 경우 이 파일을 읽어 경로를 확인한다.
검증 폴더의 AGENTS에는 짧은 입력 세 개를 해당 단계로 연결해 두었다.
이후에는 **`훅 실험` → `듀얼 검수` → `결과 정리`**만 직접 입력해도 된다.
짧은 입력을 알아듣지 못하면 아래 상세 요청을 사용하며 자동 발견 성공으로 처리하지 않는다.

## 사용자 조작 — 새 세션과 정상 훅 신뢰

새 터미널에서 준비기가 출력한 검증 폴더로 이동해 실행한다.

```bash
cd <fixture 경로>
bash .harness/codex.sh
```

1. 정상 프로젝트 신뢰 화면이 나오면 **검증 폴더**인지 확인한다.
2. `/status`에서 Sol·실제 effort·권한을 확인한다.
3. `/hooks`에서 SessionStart·Stop 두 훅을 읽고 정상 절차로 신뢰한다.
4. 신뢰 전 SessionStart가 건너뛰어졌을 수 있으므로 이 세션을 종료하고 같은 명령으로 다시 연다.

체험용 훅 명령은 `.harness/state/practice_hook_trace.py`다. 이 어댑터는 설치된 실제
`.harness/harness.py hook`에 입력을 그대로 전달하고 출력·종료 코드를 반환하며 결과만 기록한다.
검증 폴더에서만 쓰는 추적 설정이다. 최종 과제의 원래 훅 정의를 신뢰한 것과는 구분한다.
신뢰·훅 설정이 관리 정책으로 차단되면 미지원으로 기록한다. 신뢰 우회 플래그나 전역 설정 변경은 하지 않는다.

## 입력 2 — 실제 Stop 차단 유도

재시작한 검증 폴더의 Codex에 입력한다.
짧은 입력은 `훅 실험`이다.

> 지금은 훅 실험이야. probe_marker.py의 VALUE만 0에서 1로 바꾸고, 이 턴에서는 먼저 verify를 실행하지 말고 종료를 시도해줘. 실제 Stop 훅이 검증을 요구하면 그때 `python3 .harness/harness.py verify`를 실행하고 종료해. hook 명령을 직접 호출해 이벤트를 흉내 내거나 결과를 꾸미지 마. practice_app.py는 수정하지 마.

기대 흐름은 다음과 같다.

1. 새 세션의 실제 SessionStart가 기준 상태를 저장한다.
2. VALUE 변경 후 첫 Stop이 `decision: block`으로 이어서 검증을 요구한다.
3. Codex가 verify를 실행한다. `practice-marker-only`가 통과한다.
4. 다음 Stop이 허용되고 최신 영수증이 남는다.

모델이 첫 Stop 전에 선제 검증했다면 **Stop 차단은 미검증**이다. 그 결과를 훅 성공으로 바꾸지 않는다.
직접 `hook`에 가짜 JSON을 넣는 시험은 핵심 함수 점검일 뿐 실제 콜백 활성화의 증거가 아니다.

## 입력 3 — Sol + Sol 듀얼 리뷰

다음 요청은 검증 폴더의 메인 Codex에 입력한다. 검수 대상에는 고의 오류가 있으며 수정하지 않는다.
짧은 입력은 `듀얼 검수`다.

> practice_app.py를 PRACTICE_TASK.md 기준으로 Sol 두 개의 새 독립 컨텍스트에서 검수해줘. 이전 대화·작성자의 결론·이 문서·이전 리뷰 결과는 전달하지 마. 공통 입력은 요구·대상 코드·프로필·원칙뿐이야. A는 요구·정확성·회귀, B는 권한·입력 경계·실패 조건에 중점을 두되 둘 다 정확성과 보안을 봐. 코드 수정·스타일 조사·추가 에이전트 없이 각 10줄 이내로 근거를 반환해. 시작·종료 코드 지문과 실제 두 호출·응답·모델을 보여주고, 지원하지 않으면 듀얼 실행 실패라고 말해줘.

우선 `kty_reviewer`를 **부모 대화 전체를 전달하지 않는 새 컨텍스트**로 두 번 호출한다.
동일 세션 역할 전환은 금지한다. 해당 모드가 없거나 막히면 30초 안에 제한을 기록하고,
허용되는 경우 다음의 별도 읽기 전용 CLI 두 개를 실행한다. 두 명령은 각각 새 Codex 세션이다.

```bash
python3 .harness/harness.py review 'PRACTICE_TASK.md와 practice_app.py를 읽고 정확성과 보안을 검수하라. A: 요구·정확성·회귀 중심. 다른 리뷰·runbook·준비기·이전 결론을 읽지 말라. 스타일 조사·수정 없이 10줄 이내로 입력과 근거를 반환하라.'
python3 .harness/harness.py review 'PRACTICE_TASK.md와 practice_app.py를 읽고 정확성과 보안을 검수하라. B: 권한·입력 경계·실패 조건 중심. 다른 리뷰·runbook·준비기·이전 결론을 읽지 말라. 스타일 조사·수정 없이 10줄 이내로 입력과 근거를 반환하라.'
```

가능하면 두 호출을 병렬 실행하되 결과를 서로에게 전달하지 않는다. 별도 CLI도 차단되면
호출 실패를 기록한다. 메인이 두 결과를 대신 쓰거나 한 리뷰를 두 개로 세지 않는다.
모델·effort·시간과 독립 실행 지원은 실제 표시·도구 기록으로 판정하며 자기 보고만으로 확정하지 않는다.

### 부모 AI가 capacity로 멈췄을 때의 터미널 대체

반입된 이 문서 안의 명령을 사용한다. 검증 폴더에서 `.harness/work`를 만들고
검토 전 지문을 `review.before`에 기록한다. 두 터미널을 쓰면 각 명령을 하나씩 실행한다.

```bash
mkdir -p .harness/work
python3 .harness/harness.py fingerprint > .harness/work/review.before
```

터미널 A:

```bash
python3 .harness/harness.py review 'PRACTICE_TASK.md와 practice_app.py만 대상으로 정확성과 보안을 검수하라. A: 요구·정확성·회귀 중심. 다른 리뷰·runbook·준비기·이전 결론을 읽지 말라. 임시 파일 없는 python3 -B -c로 재현하고 수정 없이 10줄 이내로 반환하라.' > .harness/work/review-A.out 2> .harness/work/review-A.err
printf '%s\n' "$?" > .harness/work/review-A.exit
```

터미널 B:

```bash
python3 .harness/harness.py review 'PRACTICE_TASK.md와 practice_app.py만 대상으로 정확성과 보안을 검수하라. B: 권한·입력 경계·실패 조건 중심. 다른 리뷰·runbook·준비기·이전 결론을 읽지 말라. 임시 파일 없는 python3 -B -c로 재현하고 수정 없이 10줄 이내로 반환하라.' > .harness/work/review-B.out 2> .harness/work/review-B.err
printf '%s\n' "$?" > .harness/work/review-B.exit
```

양쪽 명령이 끝난 뒤 지문을 `review.after`에 기록한다. 완료되지 않은 세션은 정상 중단하고 미완료로 기록한다.

```bash
python3 .harness/harness.py fingerprint > .harness/work/review.after
```

결과 정리 단계에서 A/B의 `.out`, `.err`, `.exit`와 전후 지문을 함께 읽도록 한다.
실제 CLI 시작부의 모델·서로 다른 session id, 종료 코드, 각 응답을 대조한다.
파일이 있다는 사실만으로 성공 처리하지 않는다. 메인이 이 대체 실행을 보지 못했으므로
출력 경로를 전달하지 않으면 실제로 끝난 리뷰도 미확인으로 요약할 수 있다.

## 입력 4 — 결과 정리

짧은 입력은 `결과 정리`다.

> .harness/state/practice-fixture.json의 보고 명령으로 이 폴더를 점검해줘. .harness/work에 터미널 대체 리뷰 출력·시작 메타데이터·종료 코드·전후 지문이 있으면 그것도 읽고 대조해줘. 설치·실제 훅 콜백·현재 영수증·Sol 두 독립 호출·검수 결과·미지원 항목을 근거와 함께 요약하고, 실행 안 한 항목은 미확인으로 남겨. 새 설치나 리뷰는 시작하지 마.

제공 Codex가 실행할 명령:

```bash
python3 <반입경로>/scripts/practice_probe.py report <fixture 경로>
```

| 항목 | 통과로 볼 근거 | 부족할 때의 판정 |
| --- | --- | --- |
| 공개 반입·설치 | 실제 clone·설치 종료 코드와 검증 폴더 | 원인·환경·미확인 범위 기록 |
| Skill/역할 | 실제 읽기·발견 또는 호출 기록 | 파일 존재만 확인한 것과 구분 |
| SessionStart | 네이티브 실행에서 남은 추적 이벤트와 세션 기준 파일 | 미확인/미지원 |
| Stop | 같은 session_key의 차단 → 영수증 이후 해제 | 선제 verify나 수동 이벤트면 차단 미검증 |
| 최종 영수증 | report의 `receipt_current: true` | 오래됨/실패/미실행 |
| 두 독립 리뷰 | 실제 두 agent 또는 CLI 세션 시작·응답, 두 모델 Sol | 자기 보고·같은 세션 두 답변이면 미확인 |
| 동일 코드 | 전후 지문 일치와 `review_fixture_unchanged: true` | 중간 변경이면 공통 상태 검수 미충족 |
| 검수 품질 | 관찰자용 예상 결함과 실제 응답 대조 | 실행 성공과 결함 탐지 부족을 따로 기록 |

report는 기록된 콜백·영수증·검수 파일 변경만 확인한다. 듀얼 리뷰 실행은 자동 판정하지 않는다.
로그 JSON에는 네이티브 서명이 없으므로 실제 플랫폼의 콜백·호출 기록과 함께 대조한다.

### 관찰자용 예상 결함 — 리뷰어에게 전달하지 않음

- 합계: `[2, 3]`이 6, 빈 배열이 1을 반환한다. 요구는 각각 5, 0이다.
- 권한: 사용자 `other`가 owner_id `owner`인 문서에도 접근을 허용한다.
- 두 리뷰가 각자 어떤 결함을 근거와 함께 찾았는지 기록한다. 실행 지원 여부와 탐지 품질은 별도 판정한다.
- marker 검사는 훅 연동만 검사한다. 고의 오류가 남아 있어도 marker가 통과하므로 앱의 정확성·보안 검증으로 주장하지 않는다.

13분 이후에는 관찰한 버전·명령·오류와 미확인 사항을 작업 공간 안에 남기고,
사용자가 미리보기·저장·체험 종료 흐름을 확인한다. 실행 중인 테스트 세션은 정상 종료한다.
접속 코드·키·문제 원문을 외부로 복사하거나 결과를 push하지 않는다.
사전체험 관찰 후 하네스 수정은 로컬에서 진행하되 실제 시험 문제를 공개 저장소에 넣지 않는다.
