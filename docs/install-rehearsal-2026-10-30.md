# 한 번의 설치 요청 리허설 — 2026-10-30

**읽기 전용 상태에서 전체 설치·훅·듀얼리뷰까지 무중단 완료하는 것은 실패했다.**
사용자 터미널 설치와 정상 훅 신뢰를 먼저 수행한 경우에는, 새 Codex에
`하네스 설치해줘` 한 번만 전달하여 과제 설정·검증·Sol 두 독립 리뷰까지 이어졌다.
이 선행 조치를 빼고 “한 번에 설치 성공”이라고 해석하면 안 된다.

환경: 로컬 macOS, Codex CLI 0.165.0, 공개 저장소 커밋
`36b2f9fcb542ef6a9cf59226da7a047e0689c6e5`. Probe가 아니다.
effort는 실행 인자로 강제하지 않았고 실제 세션 기록에서 low를 관찰했다.
[기계 판독 결과와 증거 해시](install-rehearsal-2026-10-30.json)를 함께 제공한다.

## 실제 진행 결과

세 환경 모두 입력은 정확히 `하네스 설치해줘`였다. 합성 수율 계산 과제의 README에
실제 과제 루트·테스트 명령·반입 저장소 위치를 제공했다. 공개 저장소는 로그인 없이 새로 clone했다.
저장소 탐색·clone·사용자 타이핑 시간은 아래 실행 시간에 포함하지 않았다.

| 환경 | 소요 시간 | 실제 결과 |
| --- | --- | --- |
| read-only, 승인 불가 | 39.166초 | 파일 설치 불가. 프로필·Skill 직접 읽기, 기존 테스트 2개 통과. 설정 저장·훅·리뷰 미실행을 정확히 보고 |
| workspace-write, 승인 불가 | 173.618초 | `.codex`·`.agents` 보호로 전체 설치 생략. 쓰기 가능한 문서형 설정, 테스트 2개, 두 독립 Sol 리뷰 수행 |
| 사용자 터미널 설치·정상 훅 신뢰 후 workspace-write | 110.702초 | 기존 설치 확인, 프로필·checks·근거 갱신, Skill·역할 발견, 두 독립 kty_reviewer 검수, 최종 verify 성공 |

별도의 `codex sandbox` 내장 `:read-only`·`:workspace` 진단에서도 일반 파일과
`.codex`·`.agents` 파일 쓰기를 비교했다. read-only는 모두 차단했고,
workspace는 일반 파일만 허용하고 두 설정 경로는 `Operation not permitted`로 차단했다.
이 진단은 실행 세션과 별도의 임시 폴더에서 수행했다. CLI의 기존 `--sandbox` 모드 세션과
내장 permission profile 진단은 각각의 기록을 구분해 보존했다.

터미널 설치는 로컬 시험 제어기가 에이전트 샌드박스 밖에서 설치 명령을 실행하여
허용된 사용자 터미널을 재현한 것이다. Codex가 자신의 권한을 확장한 것이 아니며,
Probe의 사용자 터미널에서도 가능하다는 증거는 아니다. 프로젝트·훅 신뢰는 정상 TUI에서
정의를 확인하고 수행했다. 우회 플래그·신뢰 설정 직접 주입은 사용하지 않았다.

## 독립 리뷰 근거

- 문서형 설정에서 2개, 전체 설치 후 설정에서 2개, 총 4개의 독립 리뷰 세션을 확인했다.
- 런타임 `turn_context`에서 모두 `gpt-6.1-sol`, effort low를 확인했다.
- 전체 설치 후에는 `kty_reviewer` 역할이 발견되어 A·B를 새 컨텍스트로 호출했다.
  양쪽은 같은 파일 지문을 대조했고 서로의 첫 결론을 입력으로 받지 않았다.
- 차단 지적은 없었다. A의 경미한 프로필 우선순위 명확화 권고를 메인이 반영하고
  영향 범위를 확인한 뒤 최신 verify를 수행했다. 이 후속 확인은 추가 독립 리뷰로 계산하지 않았다.
- 네이티브 자식의 기술적 샌드박스는 부모의 workspace-write를 상속했다.
  수정 금지 리뷰 지침을 적용했으며 이를 OS가 강제하는 read-only 프로세스로 표현하지 않는다.
- 메인 모델에는 실제 모델·effort 텔레메트리가 노출되지 않아 보고를 보수적으로 제한했다.
  시험 제어기가 별도 런타임 기록으로 확인한 결과와 메인의 자체 보고를 구분한다.

## 실제 훅 시험

전체 설치 후 별도 요청으로 27.462초 동안 수행했다. 이는 설치 요청 외 추가 시험이다.

1. 수정하지 않은 설치본 훅 정의와 코어를 그대로 사용했다. 추적용 wrapper는 넣지 않았다.
2. 실제 SessionStart가 해당 세션 ID의 기준 지문 파일을 생성했다.
3. 과제 소스에 동작을 바꾸지 않는 주석만 추가하고 verify 없이 `READY`로 종료를 시도했다.
4. 런타임이 `hook_prompt`로 “최신 코드의 검증 성공 기록이 없습니다”를 전달했다.
5. Codex가 checks를 확인하고 verify를 실행했다. 테스트 2개 통과 후 턴이 완료됐다.
6. 최종 영수증 `passed=true`와 현재 파일 지문 일치를 별도로 대조했다.

가짜 이벤트 JSON이나 hook 직접 호출을 성공 증거로 사용하지 않았다.
설정 담당 Codex는 신뢰 상태를 직접 관찰하지 못해 `/hooks` 확인을 남은 조치로 보고했다.
시험 제어기가 수행한 정상 신뢰와 후속 실제 콜백 증거로 이 부분을 확인했다.

## 반영과 한계

README와 설치 후 지침에 전체 읽기 전용·설정 경로 보호·허용된 사용자 터미널 설치를
구분하도록 보완했다. `--no-hooks`도 두 설정 경로에 쓰므로 해결책이 아님을 명시했다.
이미 설치했다면 재설치 대신 남은 과제 설정부터 진행하도록 안내했다.
이 보완은 문서 변경이며 리허설에 사용한 런타임 코드와 다르지 않다.

임시 프로젝트·훅 신뢰 항목은 제거하고 다른 사용자 설정은 보존했다.
원시 로컬 실행 기록에는 개인 지침이 포함될 수 있어 공개하지 않으며, 공개 결과에는
필요한 실행 사실·세션 해시·증거 해시만 담았다. 실제 Probe의 권한·역할·훅 지원 및
실제 문제 해결·제출·15분 체험 완료는 이 리허설로 보장되지 않는다.
